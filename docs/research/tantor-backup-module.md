# Модуль бэкапов платформы Tantor: функции и устройство

Исследование по тикету [#2](https://github.com/dimda7/backup/issues/2). Дата обращения ко всем источникам: 2026-10-07.

Источники — только первичные: официальная документация Платформы Tantor 7.0 и ПАК Tantor XData 3.3 (и 3.2 для истории) на `docs.tantorlabs.ru`, включая примечания к выпускам. Термины нашего проекта (Сервер управления, Хост БД, Хранилище, Политика бэкапа) взяты из `CONTEXT.md`; термины Tantor даны в кавычках или как имена собственные.

Пометки достоверности:

- **[док]** — прямо написано в документации (ссылка рядом);
- **[вывод]** — моя интерпретация, в документации прямо не сказано;
- **[не подтверждено]** — искал, не нашёл.

## Короткий ответ

Модуль на WAL-G в экосистеме Tantor называется **Backman**. Это не часть самой Платформы Tantor, а «система резервного копирования XData» — программно-аппаратного комплекса Tantor XData; Платформа лишь подключается к нему как к внешней системе и даёт веб-интерфейс [док: [релиз 6.1.1][tp-rn-611], [архитектура Платформы][tp-arch]]. Для обычных экземпляров вне XData Платформа документирует только интеграцию с RuBackup, причём в режиме просмотра: создание и восстановление открывают интерфейс RuBackup (Tucana) [док: [общая страница][tp-backup-info], [страница «Резервные копии»][tp-backup-mon]].

Поэтому ориентир для нас складывается из двух слоёв:

1. веб-интерфейс Платформы для Backman — что видит и делает пользователь;
2. сам Backman (сервер, CLI, API) — как это устроено и какие есть возможности сверх интерфейса.

## 1. Что есть в Платформе Tantor (веб-интерфейс)

### 1.1. Подключение системы резервного копирования

- На тенант можно подключить только одну систему резервного копирования; страница «Настройки тенанта» → «Резервное копирование» [док: [backup.html][tp-backup]].
- Поля подключения: FQDN/IP сервера, порт, имя пользователя, пароль, название базы данных; есть изменение (с повторным вводом пароля) и удаление подключения [док: [backup.html][tp-backup]]. Страница не уточняет, одинаковы ли поля для RuBackup и Backman [не подтверждено].
- Поддерживаемые инструменты в фильтрах и столбцах: «RuBackup» и «Backman» [док: [backup_monitoring.html][tp-backup-mon]].

### 1.2. Наблюдение

Всё ниже — [док: [backup_monitoring.html][tp-backup-mon]], если не указано иное.

- Список бэкапов на трёх уровнях: тенант, рабочее пространство, конкретный экземпляр.
- Столбцы списка: кластер, домен/IP, кластер или экземпляр, тип (полный, дифференциальный, инкрементальный), статус, инструмент, начало, завершение, размер, пространство. На странице экземпляра дополнительно «Срок действия».
- Статусы: «завершено», «в процессе», «неуспешно», «запланировано».
- Поиск по домену/IP; фильтры по пространству, кластеру/экземпляру, инструменту, типу, статусу; настройка столбцов таблицы.
- Сводка по экземплярам и кластерам: число полных, инкрементальных и дифференциальных бэкапов, дата, размер и статус последнего бэкапа.
- Тепловая карта бэкапов за последний год (только Backman): по дням видны успешные и неуспешные бэкапы, щелчок по дню открывает список копий за дату. Появилась в 6.4.0 [док: [релиз 6.4.0][tp-rn-64]].
- «Посмотреть логи» для отдельного бэкапа (только Backman).
- На плитке рабочего пространства — индикатор числа невыполненных бэкапов; щелчок открывает список, отфильтрованный по пространству и статусу «Неуспешно» [док: [admin_tiles.html][tp-tiles]].
- На странице «Обзор» экземпляра — время создания последнего бэкапа; прочерк означает, что интеграция не настроена [док: [overview.html][tp-overview]].
- Пользователю с правами только на просмотр стратегии должны быть видны: их отсутствие исправлено как ошибка [док: [релиз 6.4.1][tp-rn-641]]. Полного описания того, что доступно такой роли в разделе бэкапов, нет [не подтверждено].

Оповещения именно о бэкапах (письмо, мессенджер при неуспехе) в описании страницы «Оповещения» и в страницах бэкапов не упоминаются [не подтверждено: подстраницы раздела оповещений целиком не просматривал].

### 1.3. Запуск бэкапа вручную

- Кнопка «Создать бэкап»: выбор пространства, кластера и типа — полный, инкрементальный или дифференциальный [док: [backup_monitoring.html][tp-backup-mon]].
- Нельзя создать инкрементальный бэкап, если для кластера ещё нет полного [док: там же].
- На странице реплики создавать и восстанавливать бэкапы нельзя — только на мастере кластера [док: там же].

### 1.4. Расписание и хранение — «Стратегии»

Появились в 6.3 [док: [релиз 6.3][tp-rn-63]]. Всё ниже — [док: [backup_monitoring.html][tp-backup-mon]].

- Стратегия — «правила и методы создания, хранения и удаления резервных копий». Это ближайший аналог нашей Политики бэкапа, но с отличием: одна стратегия несёт один тип бэкапа.
- Поля: название (до 50 символов), пространство, тип бэкапа (полный, инкрементальный, дифференциальный), описание (до 255 символов).
- Расписание:
  - дата начала действия и необязательная дата окончания;
  - периоды запуска (окна) — минимум 1 час, до 6 периодов;
  - повторы по месяцам, неделям или дням; можно задать числа от начала или конца месяца либо «N-й день недели месяца» (например, первый вторник).
- Политика удаления: число дней хранения и максимальное число хранимых копий.
- Привязка: стратегия создаётся отдельно, затем к ней привязывают кластеры; отвязка — с подтверждением вводом слова. Стратегию с привязанными кластерами удалить нельзя.
- В интерфейсе показываются даты следующих запусков [док: исправление в [релизе 6.3.1][tp-rn-631]].

### 1.5. Настройки WAL-G

Появились в 7.0.2, только для Backman, окно на странице бэкапов экземпляра [док: [релиз 7.0.2][tp-rn-702], [backup_monitoring.html][tp-backup-mon]]:

- интервал проверки активности;
- метод сжатия: lz4, lzma, zstd, brotli;
- порог размера tar (минимум 8388607 байт);
- лимит фоновых выгрузок WAL;
- число параллельных скачиваний и повторов при скачивании;
- число параллельных выгрузок и параллельных операций с диском.

Параметры Хранилища (адрес S3, бакет, ключи), шифрование бэкапов и число дельта-шагов в интерфейсе Платформы не описаны [не подтверждено].

### 1.6. Восстановление

- «Восстановить» → выбор: «в текущий кластер» или «в другой кластер» [док: [backup_monitoring.html][tp-backup-mon]].
- В текущий кластер — подтверждение вводом слова «восстановить»; в другой — выбор пространства и кластера [док: там же].
- Восстановление на указанное время в интерфейсе существует: примечания к 7.0.2 упоминают исправление ошибки «при восстановлении резервной копии на указанное время» для Backman [док: [релиз 7.0.2][tp-rn-702]]. Как выглядит выбор времени в интерфейсе, страница не описывает [не подтверждено].

### 1.7. Удаление

- Удаление отдельного бэкапа из меню, с подтверждением вводом слова «удалить» [док: [backup_monitoring.html][tp-backup-mon]].

### 1.8. Проверка бэкапов

Отдельной функции проверки бэкапа (пробное восстановление, проверка целостности, аналог `wal-g wal-verify`) в документации Платформы нет [не подтверждено]. Что есть близкого — см. раздел 2.6.

## 2. Backman: возможности и устройство

Источник всего раздела — [руководство пользователя Backman, XData 3.3][xd-backman], если не указано иное.

### 2.1. Компоненты [док]

- **Backman Server** — контейнер с API на порту 8000; пример развёртывания — `docker-compose`.
- **Собственная база данных** Backman — PostgreSQL (образ Tantor BE 15) в соседнем контейнере.
- **backman_s3_proxy** — отдельный сервис: порт 8009 (S3 API) и 8010 (управление). Через него выдаётся доступ к объектам бэкапа; при экспорте API возвращает временные ключи с полем `expired_at` [док: [экспорт копии][xd-export]].
- **Vault** — PKI-хранилище сертификатов и JWT-токенов; альтернативный режим `SECRETS_MANAGEMENT=backman`.
- **Backman CLI** (`backman-cli`) — Python-пакет, ставится через `pip`; общается с сервером по mTLS.
- **REST API** — `/api/v1/...` (например `/api/v1/job/`, `/api/v1/backup/<id>/objects`, `POST /api/v1/backup/restore/run`), пространство имён передаётся заголовком `ns` [док: [экспорт копии][xd-export], [что нового XData][xd-rn]].
- **Журналы заданий** уходят в Loki (обязательный параметр `LOG_SYSTEM__URL`).
- **TAM** (Tantor Appliance Manager) — управляющий сервис XData; Backman синхронизирует с ним список кластеров по интервалу `SCHEDULE__CLUSTER_SYNC_INTERVAL`.
- **Планировщик** — «раннер обработки стратегий» внутри сервера, по умолчанию раз в 1800 секунд (`SCHEDULE__BACKUP_RUNNER_INTERVAL`).

### 2.2. Агент на узлах БД

- До XData 3.2 включительно существовал **Backman Agent** на вычислительных узлах: «Восстановление происходит на всех вычислительных узлах с инстансами кластера, где установлен агент Backman»; у заданий было поле `agent_id`; была команда `backman-cli agent unregister` [док: [руководство Backman, XData 3.2][xd-backman-32], [что нового XData, раздел 3.2][xd-rn]].
- В 3.2 настройки WAL-G перенесли из конфигурации каждого агента на сервер, на уровень кластера: «больше нет необходимости менять конфигурацию каждого агента» [док: [что нового XData][xd-rn]].
- В 3.3 агент убран: «Устранена зависимость от компонента Backman Agent... система резервного копирования Backman стала самодостаточной» [док: [что нового XData][xd-rn]].
- Как именно сервер 3.3 запускает WAL-G на узлах без агента, документация прямо не объясняет. Косвенные признаки: у сервера есть настройки подключения к TAM (адрес, сертификаты); TAM упоминает «выполнение операций Patroni, WAL-G»; отмена восстановления делает «повторные попытки запросов к TAM»; при удалении кластера «удаляются скрипты резервного копирования, настройки Patroni» из контейнеров кластера [док: [что нового XData][xd-rn]]. **[вывод]** В 3.3 роль агента выполняет TAM, а в контейнеры кластера кладутся скрипты бэкапа. Схемы компонентов в документации не нашёл [не подтверждено].
- Применение настроек WAL-G к кластеру «выполняется около минуты, так как... идёт синхронизация настроек со всеми вычислительными узлами» [док].

Для справки, агент самой Платформы Tantor — другой компонент: приложение на Go, работает от пользователя `postgres`, сам подключается к Платформе (NATS TCP:4222 и HTTPS:443), входящих портов не требует, выполняет «заранее запрограммированные задачи и задачи по расписанию» [док: [архитектура Платформы][tp-arch]]. Документация не говорит, что этот агент запускает WAL-G [не подтверждено]. Планировщик задач Платформы называет «бэкапирование СУБД» среди типовых периодических задач, но это общий механизм запуска команд и скриптов, а не модуль бэкапов [док: [планировщик задач][tp-sched]].

### 2.3. Доступ и роли [док]

- Аутентификация по клиентским сертификатам (mTLS): пользователь создаёт CSR, администратор подписывает командой `backman-cli auth csr`.
- RBAC в пределах пространства имён: роли как YAML-манифесты (`resources`: namespace, cluster, storage, strategy, permission, job, backup; `verbs`: get, list, create, update, patch, delete), привязки ролей к пользователям.
- Предустановленных ролей нет — администратор создаёт их сам.
- Токены (одноразовые и многоразовые) для регистрации сервисов.

### 2.4. Что настраивается [док]

- Параметры WAL-G по умолчанию для новых кластеров — переменными окружения сервера `BACKMAN_SERVER__WALG__*`; для отдельного кластера — `backman-cli cluster config apply` (редактор или YAML-файл, который можно применить к нескольким кластерам).
- Набор параметров: `compression_method` (lz4, lzma, zstd, brotli — по умолчанию brotli), `disk_rate_limit`, `network_rate_limit`, `download_concurrency`, `download_file_retries`, `upload_concurrency`, `upload_disk_concurrency`, `total_bg_uploaded_limit`, `tar_size_threshold`, `alive_check_interval`.
- Ограничения скорости диска и сети есть в CLI, но отсутствуют в окне настроек Платформы [док: сравнение [руководства Backman][xd-backman] и [backup_monitoring.html][tp-backup-mon]].
- Хранилище задаётся один раз на сервер: адрес S3, логин и пароль в переменных окружения сервера и s3_proxy. Путь бэкапов кластера — `s3://<бакет>/<id кластера>`, внутри стандартная раскладка WAL-G (`basebackups_005`) [док: [руководство Backman][xd-backman], [экспорт копии][xd-export]].
- Настроек шифрования бэкапов (`WALG_PGP_KEY`, `WALG_LIBSODIUM_KEY`) среди параметров нет [не подтверждено].

### 2.5. Расписание и хранение [док]

- Стратегия — YAML-манифест `kind: BackupStrategy`, применяется `backman-cli strategy apply -f`; та же команда изменяет стратегию.
- Тип: `full`, `incremental` (изменения с последней копии), `differential` (изменения с последней полной; добавлен в 3.3).
- Расписание: `frequency` (daily, weekly, monthly, yearly), `interval`, `start_date`, `until`, `week_start`, `run_windows` (окна запуска с часовым поясом), уточнения по месяцам, числам, дням недели, «N-й день недели месяца», дням года. Внутри это правила RRULE (iCalendar).
- Предпросмотр ближайших окон запуска: `backman-cli strategy rrule`.
- Хранение: `retention.duration` (дни) и `retention.count` (число копий); самые старые копии удаляются автоматически.
- Связь «многие ко многим»: к кластеру можно привязать несколько стратегий, стратегию — к нескольким кластерам. При нескольких стратегиях действует наименьшее значение хранения, и удаляются в том числе копии, созданные другими стратегиями.
- Стратегию с инкрементальным типом нельзя применить к кластеру без полной копии.
- Поиск «дыр»: `cluster list --without-strategies` и `strategy list --without-clusters`.
- Чистка: `backman-cli backup delete-garbage` удаляет старые WAL-архивы, остатки неудавшихся копий и всё, что старше самой ранней сохранённой копии. Документация предупреждает: удаление WAL делает невозможным восстановление по времени.

### 2.6. Запуск, задания, восстановление, проверка [док]

- Ручной запуск: `backman-cli backup start --cluster <id> [--type ...] [--name ...]`; возвращает `backup_id` и `job_id`.
- Задание (Job) — отдельная асинхронная операция трёх типов: `dump` (бэкап), `restore`, `delete_cluster`. Есть список, детали, логи (`job logs`) и прерывание (`job abort`).
- Блокировка: на время бэкапа или восстановления кластер блокируется, параллельные операции невозможны [док: [что нового XData, 3.2][xd-rn]].
- Сведения о копии: тип, статус (`created`, `done`, `error`), путь в Хранилище, время создания и завершения, размер до и после сжатия, идентификаторы задания и стратегии; фильтр по времени; показ удалённых копий.
- Восстановление:
  - в тот же кластер — с предупреждением, что PGDATA будет удалён и конфигурация Patroni может измениться, и с подтверждением;
  - в другой кластер (`--target-cluster`) — при совпадении мажорной версии и редакции СУБД;
  - на момент времени (`--recovery-target-time`, уточнение `--before-recovery-target`);
  - без указания копии и времени берётся последняя копия.
- Прерывание восстановления «выполняет полную остановку всех связанных процессов и переводит кластер в состояние, готовое к повторной попытке восстановления»; прерывание бэкапа просто останавливает операцию.
- Экспорт копии во внешнее S3 и восстановление «голым» WAL-G (`backup-fetch`) описаны отдельной инструкцией [док: [экспорт копии][xd-export]].
- Проверка:
  - перед восстановлением Backman проверяет «наличие непротиворечивой истории сегментов WAL», нужной для PITR; флаг `--no-verify` отключает проверку;
  - `backman-cli config check` показывает живость сервера, его базы и s3_proxy;
  - WAL-G сам опрашивает СУБД во время `backup-push` (`alive_check_interval`) и завершает бэкап ошибкой при отсутствии ответа.
- Регулярной проверки самих бэкапов (пробное восстановление, контроль целостности по расписанию) в документации Backman нет [не подтверждено].

| Восстановление | В тот же или другой кластер, на момент времени, с подтверждением; прерывание с возвратом кластера в пригодное состояние | Платформа, Backman |

## 4. Чем эталон отличается от нашей задачи

- Backman рассчитан на кластеры Patroni внутри ПАК XData, которыми управляет TAM; наш случай — одиночные экземпляры PostgreSQL на обычных Linux-хостах с systemd. Механизм доставки команд на Хост БД из эталона напрямую не переносится [вывод].
- Возможность использовать Backman для экземпляров вне XData документация не описывает [не подтверждено]. Команда `backman-cli cluster add` позволяет добавить кластер «без синхронизации с TAM», но как при этом выполняются операции на узлах, не сказано.
- У Tantor Хранилище одно на сервер Backman, а разделение — по идентификатору кластера в пути; это совпадает с нашей моделью «у каждого Хоста БД свой префикс» [вывод].
- Стратегия Tantor несёт один тип бэкапа, и на кластер их вешают несколько; наша Политика бэкапа объединяет полные и дельта-бэкапы и хранение в одном объекте на Хост БД. При нескольких стратегиях Tantor берёт наименьший срок хранения — неочевидное правило, которого единая политика избегает [вывод].
- История с агентом показательна: Tantor начал с агента на узлах, затем вынес настройки WAL-G на центральный сервер (3.2) и убрал агент совсем (3.3) [док: [что нового XData][xd-rn]].

## 5. Что не удалось проверить

- Сайт `docs.tantorlabs.ru` отвечал нестабильно; из примерно 180 страниц документации Платформы 7.0 прочитаны все страницы о резервном копировании, архитектура, примечания к выпускам 5.3–7.0.2, планировщик задач, обзор экземпляра, плитки пространств, интеграция с XData. Остальные страницы на упоминания бэкапов не просматривались.
- Руководство пользователя TAM (`xdata/3.3/user_guide/tam.html`) загрузить не удалось, поэтому механизм запуска WAL-G на узлах в XData 3.3 остаётся выводом, а не фактом.
- Справочник Backman CLI прочитан выборочно (`backup start`, `restore start`, `config check`), не целиком.
- Скриншоты интерфейса не анализировались — только текст страниц; детали форм (например, выбор времени при восстановлении) могут быть видны только на изображениях.
- Маркетинговые материалы `tantorlabs.ru` и сторонние публикации не использовались.
- Не найдено в документации: оповещения о неуспешных бэкапах, шифрование бэкапов, регулярная проверка бэкапов, схема компонентов Backman, применимость Backman вне XData.
