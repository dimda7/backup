# Секреты: главный ключ вне базы, бэкапы средствами WAL-G не шифруются

Единственные долгоживущие секреты сервиса — ключи доступа к хранилищам. В базе сервера управления они лежат зашифрованными главным ключом, который передаётся контейнеру при запуске в файле или переменной окружения и в базе не хранится. Сами бэкапы WAL-G не шифрует: полагаемся на шифрование на стороне S3 и защиту канала, поэтому ключей шифрования бэкапов в сервисе нет.

- **Главный ключ.** Без него сервер управления не стартует. Он защищает от утечки копии базы отдельно от машины, но не от взлома самой машины. Его резервная копия — обязанность администратора, отдельно от бэкапа базы сервиса.
- **На хосте БД.** Ключи хранилища лежат открытым текстом в файле конфигурации WAL-G (владелец `postgres`, права `0600`): архивацию WAL вызывает сам PostgreSQL без агента, поэтому держать их только в памяти агента нельзя. Файл целиком ведёт сервис и кладёт его через агент.
- **Смена ключей хранилища.** Администратор меняет ключи в записи о хранилище и сам запускает применение для каждого хоста БД в интерфейсе; автоматической рассылки нет. Сервис показывает, на каких хостах БД ещё применены прежние ключи.
- **Просмотр.** Администратор может посмотреть сохранённые ключи хранилища; наблюдателю они не отдаются никогда.
- **Шифрование на стороне S3.** Его настраивает администратор хранилища как правило бакета; сервис о нём не знает и не проверяет.
- **Чего в сервисе нет.** Данные разового SSH-входа при первичном подключении не хранятся (ADR 0001).

## Considered Options

- **Шифрование бэкапов libsodium на стороне WAL-G.** Отклонено владельцем сервиса: вместе с ним появился бы ключ, потеря которого означает потерю всех бэкапов.
- **Главный ключ из пароля, вводимого после каждого запуска.** Отклонён: сервис не поднимался бы после перезагрузки без человека.
- **Автоматическая рассылка новых ключей хранилища всем хостам БД.** Отклонена владельцем сервиса в пользу ручного запуска по каждому хосту.
- **Ключи хранилища только на запись, без просмотра.** Отклонено владельцем сервиса.

## Consequences

- Ключи доступа общие на хранилище (ADR 0004), а шифрование на стороне S3 прозрачно для их владельца: любой хост БД технически может прочитать бэкапы других хостов в открытом виде.
- Тот, кто получил `postgres` или root на хосте БД, читает ключи хранилища.
- Сервис не может подтвердить, что бэкапы в хранилище действительно зашифрованы.
- Прежние ключи нельзя отзывать в S3, пока новые не применены на всех хостах БД хранилища: на отставших остановится архивация WAL.
- При потере главного ключа ключи всех хранилищ вводятся заново; сами бэкапы при этом остаются читаемыми.
