# Действия на хосте БД выполняет собственный агент

WAL-G с дельта-бэкапами обязан запускаться на самом хосте БД, а важнейшее состояние (отставание архивации, выполняющиеся и упавшие бэкапы) видно только оттуда. Поэтому на каждый хост БД ставится собственный агент с узким набором операций — бэкап, удаление, восстановление, сбор состояния, — и сервер управления в повседневной работе обращается только к нему. Постоянного SSH-ключа от всех хостов БД у сервера управления нет.

- **Направление соединений.** Все соединения открывает сервер управления: агент слушает один порт на хосте БД, состояние забирается опросом. Соединения от хоста БД к серверу управления считаются закрытыми.
- **Права.** Агент работает от `postgres`; единственное привилегированное действие — остановка и запуск PostgreSQL при восстановлении — разрешается узким правилом sudo, заведённым при первичном подключении.
- **Первичное подключение.** Агент ставит сам сервер управления по SSH, по разовым данным для входа с root-правами, которые администратор вводит в интерфейсе; после установки они не хранятся. Root на хосте БД сервису нужен только в этот момент.
- **Один способ для всех машин.** Целевой хост восстановления и тестовая машина — такие же хосты БД с агентом, отдельного пути исполнения для них нет.
- **Язык.** Агент пишется на Go и поставляется одним статическим бинарником, хотя сервер управления — на Python: независимость от системного Python на хостах БД важнее единого языка.

## Considered Options

- **SSH без агента** (ограниченный ключ, операции юнитами systemd, состояние опросом). Отклонён: состояние пришлось бы собирать опросом по SSH, многошаговое восстановление зависело бы от живого сеанса, а сервер управления держал бы ключ от всех хостов БД.
- **Ansible.** Отклонён: в организации его нет, и для регулярных операций и сбора состояния он не подходит.
- **Агент на Python.** Отклонён в пользу Go ради поставки одним бинарником.

## Consequences

- Агент — второй поставляемый компонент со своими версиями: его нужно доставлять и обновлять на десятках хостов БД, и API сервера управления и агента должны оставаться совместимыми между версиями.
- Раз хост БД не может сам обратиться к серверу управления, события (сбой архивации, конец бэкапа) становятся известны с задержкой в интервал опроса.
